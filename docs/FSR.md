## 1. 结论摘要

**总体结论：条件性可行，不宜直接承诺正式交付。已确认按“虚拟数据生成脚本 → 原型验证 → 根据验证结果深化方案”的顺序推进。**

下一步先形成扫描结果 JSON Schema 与模拟数据生成指导，作为生成脚本的准备材料；随后完成可复现的数据生成与校验，再进入离线报告原型验证。本文保留候选技术路线用于验证，不提前锁定深化方案。

业务目标明确：将分散的 Excel 对比结果转换为可下钻、可筛选排序、可关联定位的报告，减少人工跨表查找。用户补充的 Cmetrics 官方规格已提供主要汇总指标的名称、公式及若干统计边界，降低了统计语义的不确定性；但它不是完整的扫描 JSON 契约，尚不足以证明明细身份、关联结构和实际输出类型。[8]

Python 预处理、自包含 HTML、Blob Worker、内嵌压缩数据等机制有技术资料支持，可以构成候选实现路径。不过，**机制存在不等于真实 `file://` 环境已验证，也不等于百万函数规模性能已达标**。

| 评估维度 | 当前结论 | 成立条件或主要限制 |
|---|---|---|
| 业务价值 | 目标与痛点匹配 | 报告能减少跨表操作；实际效率提升须由用户任务测试验证 |
| 基础展示与交互 | 有条件可行 | 输入适配正确，浏览器只渲染有限可见记录 |

| 单文件离线运行 | 机制上有条件可行 | 目标浏览器真实 `file://` 验证通过，资产及数据全部内嵌 |

正式实施的前置条件是：正确性、离线运行、容量性能及核心定位流程全部通过原型验收。如果单文件、完整变化信息和性能门槛不能同时满足，应重新评审约束，不能静默截断数据或改为服务端产品。

### 2.2 尚未确定但可在实施中验证的事项

- 普通函数记录是否还存在未展示的稳定 ID 或独立签名字段；`method_name` 带括号不能证明已含完整签名，仍按第 4.1 节的歧义策略处理。
- 行号从 0 还是 1 开始、普通函数结束行是否包含末行；重复片段长度与物理行跨度的关系尚未明确。本次重复片段定位不依赖结束行，不据此自行反算。
- `-fp` 已确认以逗号分隔多路径；复杂引号、路径本身含逗号、相对路径、无可用公共根及两侧根目录层级改变时的边界处理仍需明确。
- 一般明细保留空容器，函数数组保留末尾最大值对象；其他字段的必填、可空、精度及跨版本类型差异仍待确认，不能由一个样例全部推导。
- 已确认忽略 `warning_suppression_total`；其依赖项 `warning_suppression_kloc` 是否同时忽略尚未单独确认，不能自行补值或将两者都写成用户已确认删除。
- 官方公式及严格大于阈值的边界与内部版本是否一致；比例序列化尺度、零分母行为，以及重复行并集在可用字段上的复核方式。
- 完整 `file_sizes` 的覆盖、目录恢复能力、实际重复组大小及其他数据分布；内部规则配置能力和现有 Python 实现的可复用程度。

以上均为明确登记的验证条件，不由建议架构自动补足。若字段能力不足，按已确认的歧义、未知和覆盖不足策略展示，不伪造事实。

### 2.3 官方规格新增的指标口径

官方表 1 给出了 43 个参数，曾用于构造初始汇总样例；用户随后删除了当前不保留的 8 个 CCA／深度字段，并补充元信息和明细。当前输入样例以用户编辑后的字段为依据，不能强制补回全部公开指标。顶层 `summary_metrics` / `detail_metrics` 来自用户的实际格式描述，不是从该网页推导出的官方 JSON 契约。[8]

与原有看护范围对应的主要字段如下。表中保留官方定义，并明确标出用户已确认的内部适配口径；其余公式的内部版本适用性仍须核验，分母为零时的输出行为不能自行推断。

| 原有看护指标 | 官方字段 | 官方定义及已确认的内部口径 |
|---|---|---|
| 非空非注释代码量 | `code_size` | 去掉空行和注释行后的代码行数；不同于包含它们的 `raw_lines` |
| 平均文件代码行 | `lines_per_file` | `code_size / files_total` |
| 平均函数代码行 | `lines_per_method` | `method_lines / methods_total`；函数行数只计函数内部有效代码，排除函数开头定义行 |
| 平均圈复杂度 | `cyclomatic_complexity_per_method` | `cyclomatic_complexity_total / methods_total` |
| 代码重复率 | `code_duplication_ratio` | `code_duplication_total / code_size × 100`，单位 `%` |
| 文件重复率 | `file_duplication_ratio` | `file_duplication_total / files_total × 100`，单位 `%` |
| 危险函数 | `unsafe_functions_total` | 官方称不安全函数调用次数，仅 clike 检查；用户确认内部统计为各文件、各危险函数名下去重行号数组的长度之和 |
| 冗余代码 | `redundant_code_total` | 注释中的冗余代码块数量；多行块注释中的冗余代码按一块计 |
| 超大圈复杂度 | `huge_cyclomatic_complexity_total` | 圈复杂度严格大于生效阈值的函数数 |
| 超大函数 | `huge_method_total` | 函数有效代码行严格大于生效阈值的函数数 |
| 超大头文件 | `huge_headerfile_total` | 有效代码行严格大于生效阈值的头文件数 |
| 超大源文件 | `huge_non_headerfile_total` | 有效代码行严格大于生效阈值的非头文件数 |
| 超大目录 | `huge_folder_total` | 直接文件和直接子目录总数严格大于生效阈值的目录数；不递归，空子目录不计入 |

还应落实以下边界：

- `code_duplication_total` 是各文件重复行数之和；同一文件内重叠片段按重复行并集去重，不能直接累加分组片段长度。例如同文件的 1–10 行与 2–11 行分别重复，该文件合计 11 行，不是 20 行。明细行号是否足以还原有效代码行仍需核验，不能直接把 `end_line - start_line + 1` 当作非空非注释行数。
- `files_total` 只统计符合语言源码后缀的非空文件；`folders_total` 不统计空目录。超大目录的空子目录定义还包括没有源码文件的子目录。因此不能直接使用磁盘文件／目录总数作为分母。
- `huge_headerfile_ratio` 和 `huge_non_headerfile_ratio` 的分母均是 `files_total`，不是分别除以头文件数、源文件数；`huge_folder_ratio` 的分母是 `folders_total`。
- `non_hfile_duplication_ratio` 的文档分母仍是 `files_total`；`non_hfile_code_duplication_ratio` 的文档分母是代码行总数，对应 `code_size`，不能擅自改为源文件代码行总数。
- 普通圈复杂度与 CCA 圈复杂度在 `switch` 的处理上不同：前者按 `case` 数增加，后者只增加 1。`cyclomatic_complexity_adequacy = (methods_total - huge_cca_cyclomatic_complexity_total) / methods_total × 100`，使用的是超大 **CCA** 函数数，不能替换为普通圈复杂度字段。
- `unsafe_functions_kloc`、`redundant_code_kloc`、`warning_suppression_kloc` 的公式为对应数量除以 `code_size` 再乘 1000。文档在 `redundant_code_kloc` 条目下说明代码行数少于 1000 时取 0；该特殊规则不能未经核验推广到其他密度指标。
- `huge_depth_ratio`、`non_hfile_code_duplication_ratio` 的文字公式未写 `× 100`，但单位标为百分比；初始样例按百分数构造。当前样例已移除 `huge_depth_ratio`，仍保留 `non_hfile_code_duplication_ratio`；保留字段的真实序列化尺度仍待确认，不能默默将文档表达差异当作已解决。
- 官方说明 `warning_suppression_*` 仅在启用 Cmetrics 规则后生效。本项目已按 Q35 忽略 `warning_suppression_total`，`warning_suppression_kloc` 的处理仍待明确，见第 2.4 节。其他字段也可能受语言、版本和启用能力限制；未启用或被忽略不等于实测为零。

**公开默认阈值仅作对照：**本次核查的页面显示更新时间为 2026-10-15，正文称当前工具版本为 `2.1.5`；这不确认内部扫描使用该版本。表 2 给出以下默认值，超大项按严格 `>` 判断：[8]

| 超大项 | 官方表 2 默认阈值 |
|---|---:|
| 普通圈复杂度函数 | 20 |
| 函数深度 | 4 |
| 函数有效代码行 | 50 |
| 头文件有效代码行 | 500 |
| 源文件有效代码行 | 2000 |
| 目录直接子项数量 | 50 |

该页没有逐版本阈值对照，也没有单列 CCA 阈值，不能从普通圈复杂度阈值推断 CCA 的生效阈值。阈值的 JSON 键已由用户通过 `summary_metrics.huge_threshold` 补充，包含 `huge_headerfile`、`huge_non_headerfile`、`huge_method`、`huge_cyclomatic_complexity`、`huge_folder`。当前示例值分别为 500、2000、50、20、50，与对应公开默认值相同；这不证明所有版本都相同，最终比较仍读取各侧输入的生效值。

### 2.4 用户补充样例的结构与证据边界

[sample.json](../sample.json) 已由用户手工补充，当前包含 35 个数值度量、3 项元信息及 7 类明细。它仍是**用于描述格式的构造样例，不是正式 JSON Schema，也不是完整一致的扫描报告**。

| 字段路径 | 样例中观察到的结构 | 解析影响与未决语义 |
|---|---|---|
| `summary_metrics.cmetrics_version` | 字符串，示例 `2.0.2` | 作为扫描工具版本，不是代码版本；不假设与公开页面的 `2.1.5` 等同 |
| `summary_metrics.huge_threshold` | 对象，包含 5 项数值阈值 | 与普通数值度量分开；按命名阈值逐项比较 |
| `summary_metrics.command` | 实际扫描的完整命令，含 `-fp` 等参数 | `-fp` 的多个路径以逗号分隔；取路径段公共根后相对化，禁止执行命令 |
| `detail_metrics.file_sizes` | 文件路径 → `[nbnc_loc, raw_line, 文件重复代码行数]`；样例 4 个文件 | 用户已确认顺序：非空非注释行、文件总行数、文件级重复行数；第三项直接用于文件重复度量，不以分组片段长度之和替代 |
| `detail_metrics.method_metrics` | 普通函数记录后固定有 1 个末尾最大值对象；样例 2 条函数记录 | 最大值分别取自普通函数的圈复杂度及 `nbnc_loc`；无函数时仍保留对象，两项均为 0 |
| `detail_metrics.code_duplication` | 组名 → 片段对象数组；样例 1 组、2 个片段 | 使用 `file_name`、`start_line`、`code_duplication`（片段长度）；兼容样例已有 `end_line`，但不依赖它定位或计算长度 |
| `detail_metrics.duplication_files` | 组名 → 文件路径数组；样例 1 组、2 个文件 | 组成员关系在单侧扫描内保留，不能把数组直接当文件记录对象 |
| `detail_metrics.unsafe_functions` | 文件路径 → 危险函数名 → 代码行号数组；样例 3 个位置 | 同一文件、同一危险函数的数组内行号已去重；一条位置可能对应同一行多次调用 |
| `detail_metrics.redundant_code` | 文件路径 → 冗余代码块起始行号数组；样例 4 个条目 | 起始行号语义已由用户确认；不因此推断所有其他位置数组也使用相同去重规则 |
| `detail_metrics.huge_folders` | 目录路径 → 数值；样例为 52、62 | 可提供超大目录自身数值；当前 `file_sizes` 未给这些目录的成员，不能据此验证成员恢复 |

**适配注意事项：**

- `file_sizes[path][0]` 为 `nbnc_loc`，`[1]` 为 `raw_line`，`[2]` 为文件重复代码行数。结构适配保留三个位置的明确映射；在完整、可比且口径一致的文件集合上，分别求和可对应 `code_size`、`raw_lines`、`code_duplication_total`，不在缺项样例上强行对齐汇总。
- 普通函数记录字段为 `file_name`、`method_name`、`nbnc_loc`、`cyclomatic_complexity`、`start_line`、`end_line`。用户已确认 `method_metrics` 固定以一个包含 `maximum_cyclomatic_complexity`、`maximum_nbnc_loc` 的对象结束。解析须同时检查对象形态、唯一性和末尾位置，不能只凭最后一项的位置跳过校验；该对象不计为函数，也不参与函数总量求和。无函数时的表示见第 4.2 节。
- 当前样例的原始键为单数 `code_duplication` 和 `redundant_code`，片段长度字段也已确认为 `code_duplication`。这些名称与初始需求中的 `code_duplications`、`duplication_code` 等不同；输入适配应记录明确映射，不要求用户将样例改成旧描述，也不自动把所有近似拼写都认作同义。
- 文件路径采用绝对路径；用户已确认从完整命令的 `-fp` 参数取得扫描路径，多路径取公共路径后相对化。示例命令与明细前缀不同是构造占位差异，不是工具缺陷；正式一致性夹具必须让这些路径相符。公共路径应按路径段计算，不按任意字符前缀截断，详见第 4.1 节。
- 用户已确认扫描器本来就不独立输出超大头文件、超大源文件、超大函数和超大圈复杂度清单。对比工具根据完整 `file_sizes`、`method_metrics` 及对应阈值派生，不能要求输入存在这四类清单，也不能将其键缺失解释成没有超限对象。
- 汇总仍使用较大构造数值，而明细仅包含少量示例。部分问题记录引用的 `c.h`、`d.h` 没有出现在 `file_sizes` 中，超大目录也缺少成员示例。这些不是 JSON 语法错误；现阶段不要求补齐所有明细，但不得据此通过汇总一致性或引用完整性验收。
- 样例中的数量为整数、均值及比例等为 JSON number；原始构造比例使用百分数（例如 `5.0` 表示 `5%`）。用户保留这些值不自动证明真实版本的小数尺度、精度和类型，特别是仍有文档歧义的 `non_hfile_code_duplication_ratio`。
- 一般明细无结果时保留字段及对应 `{}`／`[]`，不以缺失或 `null` 代替；`method_metrics` 是明确例外，无函数时仍保留两个最大值为 0 的末尾对象。其他字段约束和身份稳定性仍不能由单个样例推断；后续按已确认规则形成 JSON Schema，并单列其未覆盖的语义校验和待确认边界。
- 当前手工样例继续作为结构材料保留，不自动改写数值。后续模拟扫描数据必须先构造明细，再派生汇总并验证引用与数值约束，见第 8.1 节；不能把各汇总值分别随机生成后宣称是一致性夹具。

当前样例已移除 CCA、深度相关字段，仍保留抑制告警等额外公开指标；字段存在本身**不自动扩展首期看护范围**。用户已明确忽略 `warning_suppression_total`，本次不将其作为分析或模拟生成的必需统计目标，也不把“忽略”转成零值；样例字段保持原样。`warning_suppression_kloc` 是否同时忽略仍待确认，不能从已忽略的总数擅自生成密度值，或宣称用户已确认删除两者。

将来若重新纳入 `cyclomatic_complexity_adequacy`，须明确它是满足度，不能对所有数值字段机械应用“增长即恶化”规则。

## 3. 已确认的需求与范围

### 3.1 使用目标与业务口径

1. 面向同一代码库 baseline/current 两次扫描，帮助用户从整体变化下钻到目录、文件、函数或重复片段位置。
2. 对本次已确认的看护指标，公司口径为：**指标增长作为恶化／待评审信号**。代码量、平均文件代码行等增长同样需要组件接口人评审说明并备案。公开规格新增到样例中的其他指标不自动纳入该规则，见第 2.4 节。
3. “恶化／待评审”是业务处置口径，不代表工具已证明实际质量下降或已找到根因。已知不可比或未知的数据不能据此产生可靠恶化结论。
4. 首期提供排查证据，不自动归因，不定位责任人，不实现审批、原因填写、备案存储、CI 阻断或历史趋势平台。

### 3.2 交付与运行约束

- 先准备扫描结果 JSON Schema 与模拟数据生成指导，完成数据生成脚本后再验证原型；根据验证结果深化方案，满足交付条件后交付一个自包含 `.html` 文件。
- 报告生成阶段可以运行 Python，读取两份扫描 JSON，并复用或改造现有逻辑；Excel 不作为唯一输入或不可变接口。
- 报告阅读阶段断网双击即可使用，不启动服务、不依赖 Python、CDN、旁置数据文件或额外软件安装。
- 目标浏览器为桌面 Chrome / Edge；测试时固定并记录版本。不承诺所有浏览器、移动端或尚未测试的操作系统组合。
- 不嵌入源码正文，不自动读取本地代码库。用户根据路径、函数标识和行号转到现有 IDE 或代码平台检查代码。
- 没有已指定的前端框架、人员配置或固定上线期限。技术选型和排期须服从验证结果。

### 3.3 数据保留范围

**保留全部必要的变化信息，不要求保留全部未变化明细。**

先完成输入校验、匹配、聚合和关联，再裁剪真正不需要展示的未变化明细。保留未变化对象的数量和聚合贡献，并在页面明确说明省略范围。

以下数据不能仅因某个指标 `delta = 0` 而删除：

- 增长文件关联的重复组成员及其片段位置，包括自身没有增长的其他文件。
- 数值相同但结构、片段组成或位置发生变化的记录；是否变化必须基于实际可用字段判断。
- 匹配歧义、数据未知及必要的校验诊断记录。
- 其他指标发生变化的同一对象，以及支撑目录导航、超大目录成员查看的必要上下文。

若只有总量字段，无法判断零差值背后是否有结构变化，应声明检测能力有限，不能宣称对象完全未变。无法在资源门槛内保留必要信息时进入重新评审，禁止静默 Top N 截断。

### 3.4 可选代码元信息

对比工具允许用户分别为 baseline 和 current 手动提供：代码仓库、分支、节点、版本号。

- “节点”指 Git commit ID 或其他版本控制系统的 revision；与可读版本号分开。
- 所有字段均可选；未提供时显示“未提供”，不从文件名推断。
- 显示来源为“用户提供、未验证”，不据此证明代码来源、仓库一致性或扫描范围一致性。
- 扫描工具版本仍来自 `summary_metrics`，不得与代码版本混淆。两侧代码版本不同不构成不可比理由。

## 4. 数据可信性方案

### 4.1 文件与函数身份

**文件：**使用规范化的仓库相对路径匹配。用户确认 `command` 保存完整扫描命令，`-fp` 指定扫描代码路径；每侧从其 `-fp` 的路径集合计算公共根路径，再将该侧明细相对化。路径来源是显式扫描参数，而不是从可能不完整的明细列表猜测。

用户给出的多路径形式为 `-fp /repo/moduel-a,/repo/module-b`，即一个参数值中的路径以逗号分隔，公共根为 `/repo`。工程上采用路径段的公共祖先语义；例如 `/repo/module-a` 与 `/repo/module-b` 也应取 `/repo`，而不是字符公共前缀 `/repo/module-`。复杂引号、路径本身含逗号、相对路径等边界仍需明确支持范围或报错，不推断已获支持。路径分隔符及大小写处理必须明确，不能盲目转小写；规范化不应依赖用户机器上存在被扫描源码。

若扫描路径不具备可用公共根、明细位于根外，或两侧路径集合变化导致相对路径层级改变，应显式暴露映射／可比性问题，不静默把路径错配解释为新增和删除。相关异常处理在原型中验证。首期仍不追踪重命名或移动；路径进出表示扫描集合成员变化，不证明磁盘文件真实新增或删除。

**函数：**当前样例有起止行号，但没有独立稳定 ID、作用域或签名字段；`method_name` 示例中的 `()` 不足以证明同名冲突已解决。若后续提供经验证的身份字段可优先使用；ID 的存在也不等于稳定。起止行号主要用于定位，不能默认作为跨版本身份。

只有路径和函数名时，两侧均唯一的键才允许配对。任一侧同名冲突均进入歧义集合，不任选记录、不生成笛卡尔积。一侧缺项的解释还须结合扫描完整性。

合并前检查键基数；若使用 pandas，应采用适当的 `validate` 约束或等价检查。两侧有效原始度量仍可各自聚合，再计算整体差值；逐函数可解释变化必须标明覆盖范围，不用伪造的配对结果解释整体差值。

### 4.2 值、存在性和未知状态分开

每个对象至少在概念上区分以下状态，实际序列化格式在原型中确定：

| 状态 | 含义 | 计算规则 |
|---|---|---|
| 已观测数值 | 当前扫描提供有效值 | 可参与相应度量计算 |
| 不在扫描集合 | 完整性与成员信息支持该判断 | 对允许采用零基准的总量，可按零计算集合变化；保留缺项来源 |
| 对象存在但无该问题 | 完整问题清单支持该判断 | 相应问题指标可为零 |
| 对象存在但未超限 | 不在超限清单，不等于数值为零 | 从完整明细回补；无法回补时仅计算清单进出 |
| 未知／无效 | 字段缺失、解析失败、覆盖不明等 | 不填零，不标为改善，说明影响范围 |
| 匹配歧义 | 无法可靠一一配对 | 不输出确定的逐对象差值 |

`delta = current - baseline` 仅用于语义与单位一致、两侧值已知或已按明确规则赋零的数值。计数型清单允许使用存在性 1/0 计算进出，但也依赖清单完整性。

一般明细的正常空结果由保留的 `{}`／`[]` 表示；缺失字段或 `null` 不得被适配器静默转换成正常空结果。**`method_metrics` 无函数时仍保留唯一的末尾最大值对象**：

```json
[{"maximum_cyclomatic_complexity": 0, "maximum_nbnc_loc": 0}]
```

这只确认了两个函数最大值的空集合行为，不决定其他均值、比例在零分母时的输出。对于四类派生超限清单，其原始键本来不存在，应检查底层完整文件／函数明细，而不是把不存在的派生键视为输入缺项。

### 4.3 聚合及增长判定

- 目录树按仓库相对路径组织。常规目录度量聚合覆盖后代文件；超大目录的直接子项计数仍为非递归，两者名称和展示位置区分。
- 对可加总的度量分别计算两侧总量、有效对象数和差值。目录净变化之外保留增加、减少及歧义对象数量，避免净零掩盖内部变化。
- 平均值、比例按第 2.3 节官方公式映射，并核验内部版本和统计集合后重算，不能直接相加或平均已有平均值。分母未知或为零时不伪造结果；低代码量下的特殊密度规则单独处理。
- 对四类重点明细（文件代码行、重复代码行、函数代码行、圈复杂度）提供目录层级聚合；具体总量、均值或比例须明确单位及统计定义。
- 全局概览保留纳入分析的 `summary_metrics` 原值；明细派生结果单独标识，差异可见，不强行对齐。元信息不得进入数值汇总；第 2.4 节已忽略的指标不因输入中仍有值而重新纳入分析或被填零。
- 官方已明确重复行采用文件内并集、文件间求和的口径；用户确认文件级重复行数位于 `file_sizes[path][2]`。文件变化和目录聚合使用这一字段，重复组用于关联定位，不能累加分组片段长度或把物理行跨度直接当有效代码行。[8]
- 对已确认纳入看护、可比且有效的指标，正差值按公司口径标为恶化／待评审。新增指标须先明确方向，不能仅因值为数字就套用。显示精度与判定精度须区分，避免显示为零却不解释其增长标记。
- 比例指标同时展示两侧原值和百分点变化；相对增长率若提供，在基线为零时显示“不适用”。
- 已裁剪的未变化数据不再可展开，但其数量和汇总贡献保留。列表、汇总及覆盖提示必须使用一致的过滤范围，不能把剩余明细当作全部总体重算平均值。

### 4.4 重复代码与超大目录

**重复代码链路：**文件重复行数变化 → baseline/current 各自的重复组 → 该组所有相关片段的文件路径、`start_line` 和 `code_duplication`（片段长度）。本次不依赖重复片段的 `end_line`；不能未经确认就以 `start_line + code_duplication - 1` 反算物理结束行，也不因样例起止跨度与长度不同就判错。这不改变普通函数记录的起止行字段。

使用带扫描侧别的组标识；不同版本的相同编号不自动关联。首期不承诺重复组跨版本追踪、内容相似度匹配或新增重复根因识别。

重复组上下文可能包含未增长文件，必须进入裁剪保留集合。大组或大量重叠关系本身也可能形成容量瓶颈，不能只用文件与函数数量估算。

**超大目录链路：**扫描器给出的直接子项数量 → 从文件路径推导的直接文件和直接子目录 → 两侧扫描可见成员列表。子目录按直接成员去重，不递归列为当前目录的直接文件。

官方计数本来就不包含空子目录（包括没有源码文件的子目录），因此不应为恢复磁盘视图而将它们补入指标计数。仍需核验 `file_sizes` 的后缀过滤、扫描排除规则与目录计数是否一致。原始数量与可恢复列表数量分别展示，数量不一致时明确说明覆盖或口径差异；成员条目可仅保留名称及类型等必要字段，不必保留所有未变化度量明细。[8]

### 4.5 危险函数与冗余代码

无稳定身份时，条目进出统一解释为“扫描记录新增／消失”，不是已证实的“问题新增／修复”。例如冗余代码起始行号因其他代码插入而移动，可能表现为一条消失、一条新增。

用户已确认：危险函数数据按“文件 → 危险函数名 → 行号数组”组织，同一文件内同一危险函数在同一行调用多次，原始明细只保留一个行号。适配后的可观测记录粒度为 `(file_name, unsafe_function_name, line_number)`，不是每次调用；不能把不同危险函数在同一行的记录再次合并成一条。

官方将 `unsafe_functions_total` 描述为调用次数。[8] 用户在 Q33 明确确认，内部汇总采用去重后的位置条目数：

```text
unsafe_functions_total = Σ文件 Σ危险函数名 len(该名称下的去重行号数组)
```

因此可以从完整危险函数明细复算该汇总；`unsafe_functions_kloc` 的分子采用同一总数，零分母行为仍待确认。展示和校验应说明这是已去重的位置计数，不能用官方的概括措辞推翻内部确认，也不能还原已经丢失的同一行逐次调用数量。

冗余代码数组中的每个整数已确认是冗余代码块起始行号，按扫描块位置解释，不统计为冗余代码行数。起始行移动仍不等于问题实际新增／修复。

现有 1/空的比较值用于位置记录的进出；如果旧工具只按文件和危险函数名比较，可能丢失同名危险函数的多个位置变化，需在复用审查时核验，不能宣称已检查过现有实现。汇总和逐位置统计采用同一去重粒度，但位置移动仍可能产生一增一减，不能直接解释为问题真实新增／修复。

### 4.6 可比性与可追溯性

比较扫描工具版本、生效超限阈值、语言及可获得的扫描范围规则。用户确认当前内部场景不支持规则配置，仍以该使用约束为准；但官方规格明确部分语言可通过 Cmetrics 规则调整若干阈值，不能再将“不可配置”描述为所有 Cmetrics 版本的固有能力。[8]

官方阈值随工具版本及部分语言规则而异，指标定义使用严格大于阈值。应分别读取两侧的 `summary_metrics.cmetrics_version` 和 `summary_metrics.huge_threshold`，而不是使用网页版本或默认阈值替代。用户已确认 `summary_metrics.command` 为完整扫描命令，可以提取扫描路径及可解析参数，但仍需核对两侧范围、语言等设置；不同检出目录的绝对命令文本不相同，不应仅凭字符串不等就判为不可比。多路径已确认按 `-fp` 参数值中的逗号分隔，特殊路径编码边界按第 4.1 节处理。工具版本变化也可能意味着内部规则变化。

- 已知不一致：相关指标标记为“不可直接比较”，可以展示观测值，但不作为已确认恶化结论。
- 缺少元信息：标记“可比性未验证”。当前没有证据保证扫描范围规则存在于 JSON 中。
- 一致性要求针对扫描规则与范围定义，不要求文件集合完全一致。
- 可选代码元信息只标识对象，不替代上述检查。

建议报告记录生成器版本、内部数据格式版本、输入摘要、阈值、数据质量告警、各类记录的保留／省略数量和匹配覆盖率。阻断性结构错误应终止相关处理；局部未知必须可见，不能发布看似完整但实际缺项的结论。

## 5. 建议技术路线与替代方案

### 5.1 推荐验证的处理链路

```text
baseline/current 扫描 JSON + 可选的两侧代码元信息
  → schema 适配、完整性与可比性检查
  → 路径及字段规范化、实体身份与键基数检查
  → 对比、两侧聚合、重复组和目录关联
  → 建立必要上下文保留集合，裁剪可省略的未变化明细
  → 生成汇总、目录索引、查询数据块及质量诊断
  → 独立压缩数据块，内嵌 JS/CSS/数据，生成单 HTML
  → file:// 页面展示概览，Worker 按需处理数据，虚拟列表展示明细
```

这是供原型验证的候选路线，不是已经确定的库选型或实现；最终分块、索引、缓存及内部数据格式在原型结果明确后深化。当前先准备扫描结果 Schema、模拟数据生成指导及脚本，不提前实现完整页面。内部契约应将原始字段适配、可信对比结果及浏览器展示数据分开，避免页面继续解释历史 Excel 的隐含规则。

### 5.2 生成阶段

Python 负责跨扫描匹配、全局聚合、上下文选择和主要索引构建，尽量不把高成本对比交给浏览器。

避免一次保留两份原始 JSON、多份完整 DataFrame、merge 结果及全部序列化副本。是否采用流式 JSON 读取、分批处理、列式结构或磁盘中间表，取决于实测；不能假定现有 pandas 全量流程满足 8 GiB 门槛。

文件路径和函数名称可评估字典编码；同一函数的代码行与圈复杂度可共用身份记录，减少重复字段。按需采用 SQLite / DuckDB 等生成端中间存储是候选优化，不意味着浏览器必须内嵌数据库。

建议先写临时产物，完成校验后发布最终 HTML；生成失败不得留下被误认为完整报告的半成品。

### 5.3 浏览器阶段

- 首屏使用预计算概览与目录摘要；只渲染可见表格行，图表不一次绘制百万对象。
- 候选方案使用内嵌代码创建 Blob classic Worker，在 Worker 中解压、查询、排序及维护受控缓存；返回当前展示需要的结果。
- 使用可独立解压的数据块，评估有上限的缓存与释放策略。把整体压缩流随意切成字节段，不会自动获得随机访问能力。
- ArrayBuffer 转移可减少特定跨上下文复制；发送普通 JSON 对象图仍可能产生结构化克隆成本，不能宣称整条处理链零复制。[3][4]
- 全报告搜索和排序必须真正覆盖其声明的数据范围，不能仅排序当前页或已加载分块，却标成全局结果。必要的预计算索引也计入体积预算。
- 长操作显示进度或执行状态；内存不足、数据块损坏和不支持的浏览器能力必须明确报错。

### 5.4 单文件限制与方案取舍

`file://` 的同源行为存在浏览器差异，同目录文件也不保证可读取；所有运行必需资产必须内嵌，不能依赖旁置 `fetch`、模块、Worker 或 WASM 文件。[1][2]

Blob Worker、原生解压和缓冲区转移具有文档支持，但必须在实际目标浏览器的 `file://` 环境验证。不得要求关闭浏览器安全策略，或用 `localhost` 测试代替双击文件验收。[2–5]

| 方案 | 适配性 | 建议 |
|---|---|---|
| 完整 JSON 内嵌，主线程全量解析及渲染 | 简单但加载、内存及交互风险高 | 不作为目标规模默认路线 |
| Python 预处理 + 变化明细及必要上下文 + 内嵌分块 + Worker | 满足交付方向，可将较多计算前移 | 优先验证，性能仍需实测 |
| 浏览器内嵌 DuckDB-Wasm | 查询能力较强，但新增 WASM、Worker、扩展和内存复杂度 | 仅保留为备选，不作为首期必需依赖 |
| 本地服务／多人 Web 平台 | 可将容量压力移出浏览器 | 不符合已确认交付约束，未经重新确认不得替换 |
| HTML + 旁置数据、多文件分卷 | 可能降低单文档压力 | 不符合单文件约束，未经重新确认不得替换 |

DuckDB-Wasm 官方部署包含主库、Worker、WASM 及可能的扩展；示例中的 Blob Worker 也可能继续加载 CDN，不能因使用 Blob 就视为离线。其 `coi` 线程变体依赖 SharedArrayBuffer 和 cross-origin isolation，不能将通常通过 HTTP 响应头建立的线程能力计入普通双击文件的承诺。[6][7]

## 6. 容量与性能可行性

### 6.1 规模推导与限制

目标是每侧 10 万文件、100 万函数。两侧合计约 20 万条文件记录、200 万条函数记录，尚未计入重复片段、问题清单、多个度量表、中间索引及序列化副本。2,500 万代码行是度量规模，不是要求嵌入同等规模源码。

按用户提供的“5 万文件约 150 MB”作线性容量演示，10 万文件可能约 300 MB／侧，两侧约 600 MB。**这不是预测、上限或性能测试**：JSON 大小还取决于函数、重复片段、字段冗余和字符串分布。

候选产物规模可用下式理解，而不是按文件数量直接承诺：

```text
保留数据 = 汇总与索引 + 变化明细 + 必要关联上下文 + 歧义及诊断信息
HTML 大小 ≈ 内嵌资产与标记 + 编码后的压缩数据
```

若采用 Base64，编码文本约为压缩字节数的 4/3；在总文件 200 MiB 门槛下，扣除其他资产前，压缩数据预算也只有约 150 MiB。具体压缩率未知，不能把输入 600 MB 自动推导为产物达标。

裁剪收益主要取决于变化比例和上下文比例。大部分对象未变化时可能显著减小产物；接近全量变化、重复组巨大或歧义很多时，收益可能很小。即使文件和函数数量固定，重复片段数量及字符串长度也没有已确认上限，必须纳入压力数据分布。

### 6.2 内存与交互风险

虚拟列表只减少 DOM 和渲染工作，不减少 HTML 文档本身的字节数。单文件内嵌数据通常仍需随文档载入；延迟解压不等于浏览器不读取这些内容。

峰值阶段可能同时包含内嵌编码文本、解码缓冲区、解压结果、解析对象、索引、Worker 缓存和查询结果。压缩、分块及 Worker 都不能自动消除这些开销。精确内存倍率依赖实现及浏览器，当前无实测依据。

因此应同时测生成端和浏览器端，而非仅测表格渲染速度；全局排序／搜索也不能用分页或局部查询结果冒充。

### 6.3 已确认的原型验收目标

以下是 Q22 确认的门槛，**不是已达到的指标**。

| 项目 | 目标 |
|---|---|
| 参考设备 | 4 核或以上 CPU、16 GB 内存、SSD |
| 浏览器 | 桌面 Chrome / Edge，固定并记录测试版本 |
| 最终单 HTML 体积 | ≤ 200 MiB |
| 打开至概览可操作 | ≤ 10 秒 |
| 常用目录下钻、分页、已有索引的筛选排序 | P95 ≤ 1 秒 |
| 跨全报告搜索等较重操作 | P95 ≤ 3 秒，执行期间有反馈 |
| 报告新增的浏览器峰值内存 | ≤ 2 GiB，包含页面、Worker 及实际使用的 WASM 等相关开销 |
| Python 生成耗时 | ≤ 10 分钟 |
| Python 生成峰值内存 | ≤ 8 GiB |

MiB / GiB 按二进制单位计量；用户输入容量参考仍保留原始 MB 表述。

建议测试方案固定 CPU 型号、OS、浏览器、依赖版本、数据种子和缓存状态；以无其他报告的干净浏览器会话为基线测增量内存，不能只用 JS heap 数字代替完整开销。记录从读取两份输入到最终文件写完的生成耗时；浏览器同时记录概览可操作和数据初始化完成的时间，防止概览快速出现掩盖后续长期阻塞。

P95 使用固定任务集重复采样，并分别记录冷查询与热查询。具体样本次数和测量工具在原型测试计划中固化，结果须能够复现。

## 7. 安全、部署与维护可行性

1. **数据不外传。**开发以人工构造或合成数据为主，真实数据在公司内部运行验证；不要求上传样本、源代码或报告。
2. **零外部运行依赖。**禁止 CDN、遥测、外部字体和隐式扩展下载；在断网及干净缓存条件下检查实际请求。
3. **报告仍是敏感材料。**即使不含源码，路径、函数名、提交标识和质量数据仍可能敏感；沿用公司存储和分发规定。单文件本身不提供账号权限、撤销访问或保密保证。
4. **输入全部按不可信文本处理。**路径、函数名、分支、版本号和 `command` 等不得直接插入可执行 HTML。扫描命令只作为元数据解析与展示，禁止自动执行；其路径和参数也纳入敏感信息分发管理。处理 `</script>`、HTML 特殊字符及模板注入，避免报告成为脚本注入载体。
5. **限制隐含资源消耗。**对解析、解压和数据块完整性进行校验；异常输入应明确失败，不假定文件来源可完全信任。
6. **固定并审查依赖。**记录内嵌第三方库版本及许可证，检查构建产物无外连依赖；浏览器升级后对 `file://` 路径执行回归。
7. **单文件是静态快照。**修正输入、元信息或对比逻辑后重新生成，不承诺在线编辑、回写或跨用户共享状态。

## 8. 原型验证计划与决策关卡

### 8.1 阶段与交付证据

| 阶段 | 工作 | 通过证据 |
|---|---|---|
| P0 数据契约、模拟指导与生成脚本 | 先形成扫描 JSON Schema 和模拟数据生成指导，再实现独立、可复现的生成脚本；从明细派生两侧汇总 | Schema 与补充语义校验清单、脚本使用说明、数据种子与配置、正确性夹具和自动化断言；未覆盖范围显式登记 |
| P1 离线机制与容量最小验证 | 最小单 HTML，内嵌 Worker、数据块、解压与有限查询；尽早测试目标量级 | 真实 `file://` 断网运行记录，体积、生成及浏览器资源数据 |
| P2 核心业务流程 | 13 类结果基本展示，重点完成聚合、重复组联查、目录成员查看及歧义提示 | 代表性定位任务通过；裁剪与汇总一致性验证 |
| P3 分布压力与回归 | 两侧满规模，低／中及接近／达到全量变化，大重复组、深目录、长字符串及大量歧义 | 性能门槛逐项结果，异常处理、长时使用与内存记录 |
| 方案深化（原型验证通过后） | 根据 P1–P3 证据确定内部数据格式、分块、索引、技术选型及实施计划 | 取舍依据、正式实现范围、风险处置和重新估算的交付计划；不把候选方案当作既定结论 |
| P4 公司内部真实数据核验 | 内部人员运行固定版本工具及测试流程 | 在公司受控环境保留真实数据正确性与性能证据，不要求外传 |

按用户确认的顺序，先完成 P0 的数据生成与校验，再开展 P1–P3 原型验证，验证后深化方案。P1 仍应尽早检查目标量级，避免先打磨完整页面；不能用数据生成脚本能运行替代离线 HTML 验证。合成数据通过只能支持原型技术判断，正式交付仍需 P4。

JSON Schema 用于表达扫描输出结构，不是 `cmp_*` 对比结果结构。最大值对象唯一且位于末尾、实际最大值、汇总公式、跨字段引用和阈值派生等约束，必须在校验清单中逐项落实；不能仅因数组允许两类对象或 Schema 校验通过，就宣称这些语义均已验证。

**模拟数据必须先生成明细，再统计汇总（用户已确认）：**

1. 先生成文件与目录集合、函数度量、重复组、危险函数位置、冗余块位置等底层数据，并使所有引用指向存在的对象；路径必须与该侧命令记录的扫描根路径一致。
2. 文件数组使用已确认的 `[nbnc_loc, raw_line, 文件重复代码行数]`。文件代码行超限采用第一项；文件重复量采用第三项。结合文件类型、完整函数记录及阈值派生四类超限对象；按目录直接成员口径构造超大目录数据。由普通函数分别求圈复杂度及 `nbnc_loc` 的最大值，将唯一最大值对象放在 `method_metrics` 末尾；无函数时仍保留该对象，两项均为 0，且不计入函数数量或总量。
3. 从同一套明细计算数量、总量、最大值，再计算均值、百分比及密度。文件数由文件集合计数，`code_size`、`raw_lines`、`code_duplication_total` 分别从文件数组三项聚合；文件重复量须与生成的重复关系和有效行集合一致，不能独立随机指定。重复片段以 `start_line` 和长度 `code_duplication` 表示，不依赖 `end_line`，也不猜测长度到物理结束行的换算。尚未明确的行号、零分母等边界应登记支持范围，不能用随机数或默认零值掩盖。
4. 同一文件、同一危险函数的行号数组去重后，按所有数组长度之和生成 `unsafe_functions_total`；不同名称在同一行的记录分别保留。按用户要求忽略 `warning_suppression_total`；`warning_suppression_kloc` 的生成或忽略策略仍待明确，不擅自补值。
5. baseline/current 通过对基线明细施加有记录的增删改生成，每侧再各自重算汇总。目标变化比例由明细改动控制，不直接修改 delta 或 summary 来假造场景。
6. 校验汇总／明细一致性、引用完整性、阈值派生和既定变化预期。错误输入测试可以刻意破坏这些约束，但必须与正常模拟扫描数据分开标记。固定随机种子和生成配置以便复现。

以上适用于后续正确性夹具和压力数据；当前手工 `sample.json` 只用于描述结构，不自动重写为一致性夹具。本次未实现数据生成器。

### 8.2 必须覆盖的正确性案例

- 文件只在一侧出现、路径移动、路径规范化碰撞；`-fp` 单路径及逗号分隔多路径、相似字符前缀、两侧根层级变化及根外路径；不将扫描集合进出表述为已证实的磁盘操作。
- 同文件多同名函数、两侧基数不同、行号整体移动；无笛卡尔积，无按位置强配。校验 `method_metrics` 的最大值对象唯一且位于末尾、值来自普通函数；不得进入函数计数和总量。
- 空值的四类来源、无效数值、缺失字段与清单不完整；正常空容器与缺失／`null` 分开，未知不填零。无函数时验证唯一末尾对象的两个最大值均为 0，而非空数组；不据此把所有零分母结果也设为 0。
- 从文件／函数明细派生四类超限清单、清单进出与完整数值回补；覆盖等于阈值和大于阈值的边界，核验内部版本与官方严格大于的定义是否一致。
- 平均值与比例分母变化、零分母、零基线、百分数序列化尺度、显示舍入，以及 summary 与明细聚合不一致；覆盖普通圈复杂度与 CCA、函数定义行排除、空文件过滤和低于 1000 行的冗余代码密度规则。
- 重复组编号变化、跨文件组、零文件差值但片段变化、重复区间重叠和大组上下文保留；片段以开始行与长度定位，不依赖或反算结束行，也不通过累加片段长度替代文件重复量。
- 超大目录的直接文件／子目录去重、空目录不可见、排除项以及原始数量与恢复列表不一致。
- 危险函数在不同位置出现、同一行同名调用在源明细中去重、同一行不同危险函数不能合并；验证所有行号数组长度之和等于 `unsafe_functions_total`。覆盖危险函数及冗余代码行号移动，不把记录进出自动称为问题真实新增／修复。
- 忽略 `warning_suppression_total` 不等于实测为零；未确认处理方式的 `warning_suppression_kloc` 不得被自动填值或误纳入增长判定。
- 裁剪前后汇总与数量一致；某指标零变化但其他指标变化的实体未丢失；裁剪提示准确。
- 工具版本／阈值不同、扫描范围未知、代码元信息缺失或仅一侧填写。
- 中文、特殊字符及恶意 HTML 输入，损坏数据块，能力不支持和生成中断。

### 8.3 容量与交互测试矩阵

容量验收必须覆盖 baseline/current **每侧均达到 10 万文件、100 万函数的目标规模**，不能只将其中一侧放大；同时记录代码行度量规模、两侧对象重合率、变化比例、保留比例及上下文数量。建议至少采用以下矩阵，并逐项核对第 6.3 节门槛：

- 低变化比例：验证裁剪有效且不破坏统计与关联。
- 中等变化比例：验证常用目录查询、全局筛选排序和跨块查询。
- 接近及达到全量变化：包括变化对象比例为 100% 的合成场景，验证最弱裁剪收益下能否守住单文件和资源门槛。
- 分布极端场景：大量新增／移出、大重复组、长路径／函数名、深宽目录、大量歧义。

两款目标浏览器均需真实双击文件、断网、干净缓存测试；记录实际 OS 覆盖，不将已测平台扩展为全部平台保证。连续导航、重复查询和返回先前目录时检查缓存增长及内存回收情况。

业务任务至少包括：定位整体增长贡献目录、定位函数增长并识别歧义、从文件重复增长找到互相重复的片段、查看超大目录成员覆盖差异。与现有 Excel 流程比较操作步骤和完成耗时；当前未约定效率提升百分比，不编造收益数字。

### 8.4 决策规则

- **进入正式实现：**正确性夹具、离线机制、目标规模门槛及核心流程均通过；真实数据核验路径明确。
- **正式交付：**公司内部代表性真实数据验证通过，输入契约及兼容边界有记录。
- **暂停并重新评审：**任何关键正确性能力不足，或目标规模下单文件／资源门槛仍不满足。
- **禁止隐性降级：**不得删除必要变化明细、隐去歧义、以局部结果冒充全局查询，或自行改成服务端／多文件。

重新评审可讨论文件体积、响应时间、分析范围或交付形态，但修改必须由用户再次确认。不能把“少量变化时可用”写成“全目标规模均已通过”。

## 9. 主要风险及应对

| 风险 | 影响 | 应对与停止条件 |
|---|---|---|
| 官方规格不等于完整 JSON 契约，工具实现仍不可核验 | 类型、明细关联、适配及复用估算不确定 | 补充结构样例 + 一致性夹具 + 公司内部核验；不由单个样例推导全部必填或稳定性约束 |
| 函数或问题记录身份不足 | 假增减、全排列放大、错误归因 | 一对一检查、歧义隔离、扫描记录与问题事实分开 |
| 阈值、工具版本或范围不可比 | 将扫描变化当成代码恶化 | 对受影响指标显式降级可比性，保留原值而非误判 |
| 未变化明细裁剪破坏关联 | 重复组断链、平均值失真、目录列表缺失 | 先聚合及建保留集合，再裁剪；验证统计守恒 |
| 全量变化及关联上下文过大 | HTML 超限、打开慢或内存不足 | 尽早测试最弱裁剪场景；失败后重新评审约束 |
| 生成端多份对象同时驻留 | 超过 8 GiB，生成失败 | 分批／列式／磁盘中间处理候选，以实测选择 |
| file origin、Worker 或 WASM 限制 | HTTP 可用但双击失败 | 固定浏览器真实 `file://` 验证，不关闭安全策略 |
| 合成数据过于理想 | 原型通过但真实数据失败 | 测极端分布，真实数据在公司内部补验 |
| 敏感数据分发或 HTML 注入 | 信息泄露或脚本执行 | 零外连、文本安全编码、依赖审查、遵守公司分发规范 |
| 结果被误当成根因结论 | 误导评审备案 | 明确证据层级、匹配覆盖和扫描记录语义 |

## 10. 投入、收益与实施建议

### 10.1 工作量粗估

以下保留前期规划粗估，假设一名熟悉 Python、浏览器数据处理及前端交互的工程师承担主要开发，并有熟悉扫描器的内部人员协助核验。尚未针对本次明确的 Schema、模拟数据生成指导与可复现脚本范围拆分复核；没有现成源码检查结果，也没有确定人员安排，因此不是冻结预算或排期承诺。

| 工作包 | 初步估算 |
|---|---|
| 数据契约、输入适配设计、正确性小样本 | 3–5 人日 |
| 离线单文件机制、容量最小验证 | 3–5 人日 |
| 核心对比／聚合／关联与报告交互原型 | 6–10 人日 |
| 分布压力、浏览器回归、内部核验支持与结论整理 | 4–7 人日 |
| 原型阶段合计 | 16–27 人日 |

该估算包括必要的验证迭代，不包括等待内部材料核验的时间、扫描器修改、大规模架构返工或正式产品化。现有工具若质量和契约适配，可降低投入；若仅能复用少量解析逻辑，不能按“已有工具”大幅压缩估算。正式产品化工作量应在原型关卡通过后重新评估。

### 10.2 预期收益与成本边界

预期收益是减少人工跨表检索、筛选排序和重复组查找，以及更早识别匹配歧义和不可比数据。当前没有用户分析频次或人均耗时基线，不能给出可量化 ROI 或节省比例。

主要成本来自数据语义核验、输入版本适配、容量优化、浏览器回归和内部验收；本方案不要求持续运行的服务器，但仍有生成机器、文件存储分发和维护成本。

建议优先投入 P0–P1，以较小成本回答两个关键问题：**现有数据能否支持可信解释，以及单文件在最弱裁剪条件下是否可承载目标规模。**答案成立后，再扩大交互实现投入。

## 11. 最终判断与后续交付物

当前证据足以支持立项进行技术原型验证，尚不足以支持“百万函数离线单 HTML 已确定达标”或“现有 Python 工具可直接复用”的结论。

后续按以下顺序形成交付物，而不是等原型通过后才准备输入契约和模拟数据：

1. **生成脚本准备材料：**扫描结果 JSON Schema、模拟数据生成指导和补充语义校验清单，明确已确认规则及尚未覆盖的边界。
2. **数据准备（P0）：**独立的模拟数据生成脚本、使用说明、固定种子与配置，以及可复算汇总的 baseline/current 正确性夹具和压力数据生成能力。
3. **原型验证（P1–P3）：**单 HTML 原型，以及正确性、离线兼容性、性能和核心定位流程的验证记录。
4. **原型验证后深化：**依据实测确定内部数据格式、分块、索引和技术取舍，明确正式实现范围、兼容边界、风险处置及重新估算的交付计划。
5. **正式交付前：**完成 P4 公司内部真实数据核验，保留受控验证证据。

**本报告确认的是需求边界与验证路径，不是实现完成或性能通过。**
