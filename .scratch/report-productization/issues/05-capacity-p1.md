# 05: 正式容量机制与 P1 验证

**What to build:** 正式文件查询链路在目标规模输入下可运行，并提供正式计算、分块、传输和资源使用的可复现证据。

**Blocked by:** 04：可信输入与受限报告

Status: ready-for-agent

依据：[正式产品化规格](../spec.md)及其中引用的最新 PRD／ARCHITECTURE。沿用 GLOSSARY 术语；本票编号采用用户确认的24票拆分，替代规格中12项里程碑的任务编号引用。

- [ ] 正式格式使用版本化 manifest、字典、列式表、关系索引及独立 gzip/base64 块，具备长度／摘要／类型检查；保留本阶段支持的必要明细和关系，不用 Top N 降级。
- [ ] Python 完成本切片的匹配、完整聚合及关联，Blob classic Worker 按需请求块并查询，使用 transferable 和按字节计费缓存；不直接沿用原型全量启动加载假设。
- [ ] 使用每侧 100k 文件／1m 普通函数输入跑通完整正式生成路径，登记业务覆盖和未实现能力；本切片文件查询达标不宣称全部类型已通过。
- [ ] 测量正式 HTML ≤200 MiB、概览可操作 ≤10 秒、常用查询 P95 ≤1 秒、重操作 P95 ≤3 秒、浏览器新增峰值 ≤2 GiB、生成 ≤10 分钟且峰值 ≤8 GiB。
- [ ] 固定环境、任务及缓存口径，冷热分开，热任务至少20次并用 nearest-rank 计算 P95；保留实际查询至 DOM 更新后两帧的样本、进程 RSS 记录及页面结果。
- [ ] 包含深页、缓存驱逐后重查、损坏块及发布失败检查；资源参数先作为调优值登记，核心门槛失败即暂停评审，不削减必要数据。
- [ ] 记录正式 P1 结论、证据和保留限制；本阶段不替代后续全业务与完整分布验收。
